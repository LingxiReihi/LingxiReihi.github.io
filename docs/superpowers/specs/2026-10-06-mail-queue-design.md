# 出站发信队列（mail_queue）设计

日期：2026-10-06 · 状态：三批代码全部完成（本地 198 例绿），仅剩「把兜底 cron 加进服务器 crontab」等用户点头；未 push 未上线
需求来源：用户要求「评论通过（审核）后发送通知到评论人员」，并在追问中把额度口径改成
「60 额度每小时，**超额累计到下一小时发送**，评论时的通知同步更改此限额」。

## 1. 为什么这不是"再加一封通知信"

「超额攒到下一小时发」是一个**跨进程重启的交付承诺**。原实现里 `password_reset` 与
`comment_notify` 各有一份进程内计数，重启即清零 —— 用它做排队会静默丢信。所以必须：
新表持久化待发队列 + 一个兜底冲刷触发点（cron）+ 从表本身推导的额度与退避状态。
据此本设计按 architectural 路径走，分三批，每批有独立退出门。

## 2. 拍板记录（用户选的，不是默认）

| 项 | 决定 | 理由/代价 |
|---|---|---|
| 触发时机 | 评论**首次** `pending → approved` 时通知评论者 | 去重靠 `comments.notified_at`（持久列），所以「通过→拒绝→再通过」也只发一封 |
| 额度归属 | **全站一份总预算**：忘记密码 + 作者通知 + 评论者通知 | 三条链路抢的是同一个发信邮箱，分开计数等于没有总闸 |
| 额度数值 | **30 封/小时**（用户先要 60，接受我的反对意见后降到 30） | 60/h = 1440/天，个人 QQ 邮箱大概率触发风控；阈值我们从未测出 |
| 超额行为 | 入队延后，下一窗口自动补发 | 需要持久队列与 cron 兜底 |
| 退避 | 最近 15 分钟内 ≥3 次失败且最新一次仍失败 → 暂停整条队列到「最后一次失败 + 30 分钟」；期间若有任一封成功则不连坐 | 防"积压集中冲出→再被拒→雪球" |
| 重试上限 | 5 次后转 `dropped` 并记 warning | 防永久堆积 |
| 批量审核 | 逐条入队，靠额度与退避天然截断 | 不为批量特设第二套规则 |
| 邮件内容 | 站点名 + 内容标题 + 前台链接 + 评论者自己的评论原文（截断 300 字）+ 通过时间 | 不给其他人的邮箱 |

## 3. 关键取舍：忘记密码**不入队**

口令是明文进邮件的。排队意味着明文口令在 `mail_queue.body_text` 里躺到下一小时，
直接违反本站既有承诺「服务端不留明文，口令只出现在那一封邮件里」；而且人被锁在门外等队列毫无意义。

所以：`password_reset` 保持**直发**，但发信前查 `mail_queue.budget_left()` 这同一份额度；
额度用尽就明确报 `50300 发信额度已用尽，请稍后再试`（不排队、不改口令）。
这是"两条链路语义相反"的第二处体现：重置的邮件是交付手段（发不出去就不改库），
评论通知是旁路提醒（评论已落库，失败不回滚）。

## 4. 状态模型

`mail_queue.status ∈ {pending, sent, dropped}`。等待重试的行**仍是 pending**（配 `attempts>0`
与 `next_try_at`），不设 `failed` 状态 —— 否则会出现"failed 但其实还会再发"的两处真相。
「最近失败」因此定义为：`attempts>0 且 status∈(pending,dropped) 且 updated_at 在窗口内`。

额度与退避全部是**查询推导**，没有独立计数器：重启不失效、随时可查、也不会有漂移。

## 5. 明文与暴露面（要知情）

队列期间，评论者邮箱与评论正文以明文存在 `mail_queue` 表里。敏感级别与 `comments` 表本身相同
（同一批数据本来就在那），但确实是多了一份副本，且会随 `app.db` 一起进备份。
带明文口令的信不入队（见 §3）。访客输入只进正文，绝不进 To/From；主题就地压平换行。

- **批 3（代码已完成，cron 待用户同意）**：`app.cli` 加 `mail-drain` / `mail-status`；`docs/deployment.md` 写好那行 `15 * * * *`（避开 `0 */4` 前端重建与 `*/5` watcher），**加进服务器 crontab 需用户单独点头**。
  本地真实进程实测：连发 3 条评论 → 队列 3 行全部 `pending/attempts=1/next_try+1h`，`mail-status` 报 `paused_until=09:14`（最后一次失败 +30 分钟）→ **退避成立**；`mail-drain` 在无到期行时输出 `deferred=0`。
  实测还抓到一个设计时没想到的真缺陷：**两个 drain 并发会把同一封信发两次**（同一秒的两个评论请求后台任务互相看不见对方正在发哪行）。修法是先占位再发 —— `UPDATE ... WHERE status='pending' AND next_try_at<=now` 把 `next_try_at` 推到一小时后，`rowcount!=1` 即跳过；崩在占位之后只是晚一小时重试，不丢信。新增 `test_concurrent_drains_do_not_double_send`（修复前 3 封信发出 6 次）。全量 **198 例绿**。
